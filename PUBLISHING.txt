RECOMMENDATION: Go Public on Packagist
=======================================

The package contains zero secrets. It is architectural scaffolding — roles,
controller flow, service pattern. Nothing in it gives an attacker anything
meaningful without also having your .env. All credentials (tenant UUIDs,
client ID/secret) live in the consuming app's .env, not in the package.

Making it public removes a permanent operational tax for no security gain.


IF YOU GO PUBLIC
----------------
1. Push the repo to GitHub (public visibility).

2. Register on https://packagist.org and submit the GitHub repo URL.

3. In consuming apps, simply run:
   composer require housetrevethan/filament-auth

4. Set up a GitHub webhook so Packagist auto-updates on every push:
   - Packagist profile > your package > "Update" tab has the webhook URL
   - Add it in GitHub: repo Settings > Webhooks > Add webhook


IF YOU GO PRIVATE (not recommended)
------------------------------------
Option A — GitHub Packages + PAT
  - Requires a Personal Access Token with read:packages scope
  - Must be configured in ~/.composer/auth.json on every machine and CI runner
  - Token rotation is a maintenance burden

Option B — Satis (self-hosted)
  - You run a static Packagist mirror yourself
  - Extra infra to maintain for one package

Option C — Private Packagist
  - Polished hosted solution, but costs money


BOTTOM LINE
-----------
Go public. The operational cost of private far outweighs any benefit
for a package that contains no sensitive data.
